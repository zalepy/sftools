# sftools

[![tests](https://github.com/zalepy/sftools/actions/workflows/tests.yml/badge.svg)](https://github.com/zalepy/sftools/actions/workflows/tests.yml)

A production planner for the factory-building game [Satisfactory](https://www.satisfactorygame.com/). You say what you want to make and how fast. sftools works out the production chain down to the miners as an interactive graph, then plans the belts, pipes, splitters and mergers between the buildings. You adjust the plan to the way you want to build it.

![A plan for 10 Modular Frames a minute](src/sftools/web/guide/images/overview.png)

**Live demo:** https://sftools.onrender.com/ (on a free instance: the first visit can take about 50 seconds while it wakes up)

**How to use it:** the [user guide](src/sftools/web/guide/USER_GUIDE.md), also in the app (the Guide button, and the **?** links in the side panel).

## What it does

- Expands demand targets into a graph of production nodes, with the default or a preferred recipe for each item, and alternate recipes per node.
- Lets you shape the plan: merge nodes, switch recipes, set clock speeds (or fit the last building to the demand), take in inbound production from other factories.
- Routes by-products to where they're needed, or to a Sink, and solves the loops they can create.
- Plans the logistics of every node: belts and pipes by tier, splitters and mergers, with an editor for each node's layout.
- Several plans in tabs, and a Chain view of how they feed each other. Notes and built marks track the build in the game.

## Highlights

- **By-product loops:** a by-product used as supply can feed a node above its own maker. The engine detects the loop and can balance it, solving for the rates that make the loop close.
- **Logistics simulation:** output sides are pushed (splitters share evenly, belts back up), input sides are pulled. Suggested layouts group outputs by destination and build input manifolds; edited layouts are kept until the plan changes under them.
- **Stable node ids:** nodes are identified by their path in the chain, so recipe switches, merges, clocks and notes stay attached to the right node as the plan is recalculated.
- **A stateless server:** the browser keeps the plan and sends it whole to `/api/calculate`; the server holds no session state.
- **Browser tests without a framework:** a small harness drives headless Chrome over the DevTools protocol. CI runs them on every push, and they're run again against the deployed site after each release, once it reports the new commit. The same harness takes the guide's screenshots.

## Stack

Python 3.13 and FastAPI on the server, with uv for packaging. The front end is plain ES modules with [Cytoscape.js](https://js.cytoscape.org/) for the graphs, no build step. Tests use pytest. Hosted on Render.

## Game data

The recipes, items and buildings live in the app's own JSON files under `src/sftools/data/`. They describe the game, and any source of those numbers works. They can be gathered by exploring the game: sftools grew out of a spreadsheet planner whose data was collected that way. The current files were scraped from [Satisfactory-Calculator](https://satisfactory-calculator.com) on 2026-10-11, first to check the hand-gathered data, then kept because it's the quickest way to refresh it after a game update (see [Updating game data](#updating-game-data)). The scraper is a convenience, not a dependency: the app only reads the JSON files.

Satisfactory and its game data belong to Coffee Stain Studios. sftools is a fan-made tool, not affiliated with or endorsed by Coffee Stain Studios.

## How this was built

I set the product direction and made the design decisions: what each feature does, how it should behave in edge cases, and what to leave out. The implementation was written with an AI coding assistant (Claude Code), working from those decisions. Each feature was discussed first and recorded in a ticket, then built on a branch with tests, released, and checked by running the browser tests against the deployed site. The [tickets](tickets/README.md) record those decisions, and commits made with the assistant carry a `Co-Authored-By` line.

See [ARCHITECTURE.md](docs/ARCHITECTURE.md) for how it works, [ALGO.md](docs/ALGO.md) for the calculation, and [tickets/](tickets/README.md) for the decisions behind each feature.

## Local development

Requires [uv](https://docs.astral.sh/uv/).

```bash
uv sync                                            # create .venv with app + dev dependencies
uv run uvicorn sftools.api.app:app --reload        # http://127.0.0.1:8000
uv run pytest                                      # unit tests (about a second)
uv run pytest tests/integration                    # browser tests (needs Chrome/Edge)
uv run python scripts/screenshots.py               # refresh the user guide's screenshots
```

See [tests/README.md](tests/README.md) for the test layout.

API docs are generated by FastAPI at http://127.0.0.1:8000/docs.

### Updating game data
The JSON under `src/sftools/data/` can be edited by hand, or scraped again from [Satisfactory-Calculator](https://satisfactory-calculator.com):

```bash
uv run --group scrape python scripts/scrape/pull_all_data.py
```

See [scripts/scrape/README.md](scripts/scrape/README.md) for details.

### CI and release check
Every push runs [the tests workflow](.github/workflows/tests.yml): ruff (bug-finding rules only, see `pyproject.toml`), a JS syntax check, the unit tests and the browser tests. It reports on the commit and blocks nothing.

After pushing to master, the release check waits until the deployed site's `/healthz` reports the pushed commit, then runs the browser tests against it:

```bash
uv run python scripts/release_check.py
```

## Deployment (Render)

The service is described in [render.yaml](render.yaml):

| Setting | Value |
|---|---|
| Build command | `pip install uv && uv sync --frozen --no-dev` |
| Start command | `.venv/bin/python -m uvicorn sftools.api.app:app --host 0.0.0.0 --port $PORT` |
| Health check path | `/healthz` |
| Python version | from `.python-version` |

If the service was created by hand in the Render dashboard (not as a Blueprint), copy these settings into **Settings → Build & Deploy**.
